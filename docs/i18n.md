# Languages (i18n)

Milo is multilingual. English is the source language and the fallback; Spanish ships too.
Adding a language never touches application logic.

```
translation key → language → translated text → web UI / Telegram / spoken text
```

## Four separate language settings

They default to English and may all differ:

| Setting | What it controls | Where |
|---|---|---|
| Interface language | The admin web UI and the error messages it shows | **System → Languages** (`i18n.interface_language`) |
| Notification language | Telegram messages and other notices sent to people | **System → Languages** (`i18n.notification_language`) |
| Assistant language | The language the AI answers in: a language code, or `auto` to follow the child | **Assistant → Personality** (`gpt_settings.language`) |
| Voice (TTS) language | The language spoken aloud; empty follows the assistant language | **Assistant → Voice** (`gpt_settings.tts_language`, with `tts_speed` 0.5-2 and `tts_volume` 0-100) |

The language chosen on the first-run screen becomes the interface and notification language.
The admin page learns its language from the public `GET /api/locale` before sign-in and from
`GET/PUT /api/settings/language` afterwards; `GET /api/locales` lists the installed languages.

A person can also have their own language (**People → Language**; empty means the notification
language). Telegram writes to them in it;
if they have none, the notification language applies. Nothing is guessed from a name, country,
IP address or Telegram username: languages are always configured explicitly.

## Server side (Go)

`internal/i18n` embeds `locales/<code>/messages.json`, a flat map of `"dotted.key": "text"`.
Placeholders are written `{name}`.

```go
i18n.T("es", "telegram.not_authorized", nil)
i18n.Tf(lang, "telegram.menu_greeting", "name", user.DisplayName)
```

A missing language or key falls back to English, then to the key itself: it never crashes and
never shows an empty message. Do not put user-facing text in business logic; add a key.

(`i18n.Tf` takes alternating name/value pairs, `i18n.T` a map. `i18n.ForUser` picks a person's
language, falling back to the notification language.)

Key groups: `telegram.*` (bot messages), `assistant.*` (fixed spoken replies, parent alerts),
`skills.*` (spoken timer and reminder text), `web.err.*` and `web.notice.*` (API messages,
translated into the interface language).

### The assistant

The configured language is stated explicitly in the system prompt (for example "Always reply in
Spanish, unless the child explicitly asks you to switch language"). With `auto` the prompt says to
reply in the language the child speaks. The AI provider itself stays language-agnostic. Built-in
phrases such as "let's talk about something else" use the assistant language (English for `auto`).

### Text-to-speech

The TTS abstraction receives `language`, `voice`, `speed` and `volume` from the settings; nothing
is hardcoded. Piper takes its language and voice from the model file (`.onnx`) and honours speed
and volume; cloud voices use the voice name, speed and volume. Neither has a language parameter,
so the voice file or voice name decides the real language: choose one that matches the voice
language setting.

## Adding a language (server)

1. Copy `internal/i18n/locales/en/` to `internal/i18n/locales/<code>/` (for example `fr`).
2. Translate the values. Keep the keys and `{placeholders}`. Set `locale.name` (the language's own
   name, shown in menus) and `locale.english_name` (used in prompts for the AI).
3. Run `make test`. A test checks that every key exists and that placeholders match English.

No Go code changes. The admin web UI has its own catalogs (`web/admin/src/i18n/locales/<code>.json`):
see [development.md](development.md). A language is offered to people only when both exist.

## What is not translated

The command line (`milo install`, `milo backup`, …), log lines and audit entries stay English.
Error text that comes from lower layers (for example backup passphrase rules) is shown as is.
